The spec's promise — "the built-in types come with impls provided
by the compiler" (`07-operators.md`) — is kept as source: std::ops
carries the compiler's own table, and the spelled call runs the
row the operator's sugar names.

- **the rows** — the arithmetic four for every number (i8–i64,
  u8–u64, f32/f64), `Eq` and `Ord` for the integers and the
  `bool`: fifty-eight impls, each the plain words (`*self +
  *other`, the comparisons against `Ordering`'s ends)
- **the spelled call** — `Add::add(&n, &m)` is `n + m` said the
  long way; a plain `n + m` never comes here, the checker's binop
  asked first, so nothing changes for the operators themselves
- **`bool` through `Ord`** — the pairs the language holds no row
  of its own for find their trait's: `t > f` orders now, the
  language never comparing bools
- **the floats stay out of `Eq`/`Ord`** — a NaN equals nothing,
  itself included, so the laws do not hold; the calls are refused,
  the operators answering as the language always did
- **a mixed scalar pair keeps the language's error** — the scalar
  rows are all `Rhs = Self`, so nothing in the table answers, and
  the rewrite's words would only misdirect the report (a literal
  it cannot borrow, a method whose parameters it wants otherwise):
  `n + true` still says `'+' wants both sides the same type`.
  A pointer's `Add<usize>`, the spec's own mixed `Rhs`, is the one
  that will ask the question again — its ptr<->int casts are not
  carried by emit yet (`01-types.md`)
- **coherence across std** — a project's own `impl Add for i32`
  is the conflict the check names: the compiler's table is
  source, and two sources cannot spell one row
  (`tests/check/err/192`)
